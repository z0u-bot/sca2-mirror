# Consolidate the CSS: one base sheet, one print block, a map of the rest

CSS lives in six places, and it is hard to know which one to edit. Three files: `src/mini/lit/lit.css` (the woven page frame — tokens, typography, tables, figures, admonitions, swatch base; inlined at export by `mini.lit.page`), `docs/report.css` (report polish — `.sw-themed`, `.report-table`, quiet `<details>`, the draft badge — and the e-ink print block; baked at export and re-inlined from source at build by `set_report_styles`), and `scripts/md.css` (the site's Markdown pages, `<link>`ed by `build_site.py`, and also VS Code's `markdown.styles` in `.vscode/settings.json`, which is what the `.github-markdown-body` selectors are for). Three Python strings: `_CHIP_CSS` and `_LIGHTBOX_CSS` in `mini.reports` (injected at build), and the SVG `<style>` in `subline.py` (inside each SVG, so it stays there).

The duplication that matters is between `lit.css` and `md.css`: about 120 lines near-verbatim — `:root` tokens and dark overrides, `body` type, headings, `code`/`pre`, the booktabs table block, `img`/`video`, `blockquote`, anchor links. Each file's header says it follows the other, and they have drifted: `th, td` padding is `0.8em` in lit and `0.9em` in md, md has no `--mark` token, the monospace stacks differ. Smaller overlaps: the theme-detection selector (`body:not([data-theme=…]):not(.dark)…`) is written out once for `.mini-themed-figure` in lit.css and once for `.sw-themed` in report.css; and the print rules are split, with lit.css's `@media print` (`break-inside`/`break-after`, an 11pt body) a subset of report.css's (which also sets `@page`, `--measure`, `thead`, and 11pt on `html`).

Two claims in `docs/README.md` are stale and add to the confusion: "each report links it, so it shows live while editing" and "baked via `css_file`". Neither is true now — `mini.lit`'s live server (`render.py`) builds the page with `lit.css` alone, so a `report.css` edit is invisible under `./go serve` and shows only at export or build.

Proposed shape:

- **Base sheet.** Move the shared rules out of `lit.css` into `src/mini/lit/base.css`; `lit.css` keeps the flexbox frame, figures, admonitions, swatches, themed figures. `md.css` shrinks to the site-only rules (`body` column, `.fig-strip`, `.tags`, `pre.mermaid`, the pseudo-`dl`, the `.github-markdown-body` variants) and the build concatenates `base.css + md.css` into the served file. VS Code's preview reads the file from disk, so either keep a committed concatenation or point `markdown.styles` at both files (it takes a list). Where values differ, take lit.css's: the reports are what gets reviewed.
- **One print block.** Move the two print rules lit.css duplicates into `report.css`, leaving lit.css's `@media print` with what the frame needs on its own (`color-scheme: light`, flexbox off, `main.lit { padding: 0 }`).
- **Live server.** Have `./go serve` apply `report.css` too (`extra_head` in `render.py`, or `set_report_styles`), then correct the two README sentences.
- **Python strings.** Move `_CHIP_CSS` and `_LIGHTBOX_CSS` out to files beside `reports.py` so they are findable with `fd -e css`; they keep `Canvas`/`CanvasText` rather than the page tokens, since they must work on a page rendered without lit.css. The subline SVG style stays inside the SVG — but see the note below, which narrows what that costs and reopens where the theme should live.
- **A map.** A header comment in `lit.css` listing where the other CSS lives and how each reaches the page.

The one-off `style=` attributes in `docs/m2/*/report.py` (a few in ex-2.1.1 and ex-2.1.2; the rest are matplotlib kwargs) are fine where they are. Check the result with a `./go preview` render in both themes and a PDF print, since the base split touches table padding and font stacks.

## Notes

**2026-09-22, evidence** — Two measurements from the `pymdown-extensions` sweep, both about the subline `<style>`, which this item had set aside as "stays inside the SVG".

Inlined into HTML, an SVG's `<style>` is **not** scoped to that SVG. It joins the document's stylesheets and reaches every element on the page — checked in Chromium: a rule in the first inline SVG's block styles a rect in a second SVG that has no block of its own, and its `.class` selectors reach a plain `<div>` too. So the repeated copies were doing nothing at all. ex-2.1.1 carried eight of them, one per SVG, at 996 bytes each: 8 KB of a 86 KB page, with the Google Fonts `@import` repeated eight times in a page that is read offline.

`mini.vis.svg_figure` now keeps one copy per figure (8 blocks down to 2 on ex-2.1.1, 4 down to 1 on ex-2.1.2; the pages are about 7% smaller), and the figures are pixel-identical before and after in both themes. The surviving copy is what keeps the externalized `_assets/<name>.html` sidecar self-contained, so that constraint is met without the repeats. Blocks that differ are all kept.

That leaves the real question open rather than answered, and with one more fact against the status quo: because the block is document-scoped, two sublines on one page **cannot** theme apart — both use the `svg` selector and the later one wins for both. Verified, and now a warning in `src/subline/README.md`. So "the theme lives in the SVG" is already only true one page at a time. Moving the palette to a sheet that `lit.css` carries would make that honest, and the cost is the sidecar: opened on its own it is a bare fragment with no `<head>`, so it would lose its theme unless the exporter inlines the sheet into it once. Worth deciding with the rest of this item rather than on its own.

**2026-09-22, the palette's home** — Checked the alternative first: could the sublines go through `<img src="…svg">` the way the plots go through `<img src="…png">`, and the theme question fall away? In Chromium an SVG shown through `<img>` is an isolated document that loads nothing from the network — zero requests, where the inline copy fetches the `@import`ed face — so the text falls back to whatever monospace the machine has, and no page token reaches it (`prefers-color-scheme` does, so the light/dark switch survives; an explicit `body[data-theme]` would not). Its text is also no longer selectable, searchable, or read by a screen reader, and the SVG as generated has no intrinsic size (`viewBox` only, the width in a `style` attribute), so the `<img>` collapsed to zero width until given one. The inline choice is a live one, not a leftover: the plots are raster and carry their theme as two files; the sublines are markup and take theirs from the page. The sidecars exist for the Markdown rendition, and they already do that job.

That reopens the earlier note's trade-off from the other side. The sheet does not need to move out of the SVG for the palette to be shared — the SVG's own block can *read the page's tokens with a fallback*: `--bg-color: var(--bg, light-dark(#fff, #2a2a2a))`, `--col-text: var(--fg-muted, …)`, `font-family: var(--font-mono, "Source Code Pro", …)`. Verified: inline on a page that defines `--bg`, the SVG takes it; opened alone, it takes the fallback. So the SVG stays self-contained (the sidecar keeps its theme with no wrapping), the page themes it through `lit.css`'s tokens with no change to `mini.lit`, and a report has nothing to override. The two overrides that exist (`sub_css` in ex-2.1.1 and ex-2.1.2, both `--bg-color: light-dark(#fff, #181c1a)`, "to match the dark background of this notebook") are a Marimo-era value: the woven page's dark background is `#1f1f1f`, so today the sublines sit on a slightly different dark than the page around them. Reading `--bg` would make them match and let both lines go.

Two things go with it, both in `src/subline` (vendored, not published on its own — but its SVG is what the sidecar and the tests show with no page around it, so the defaults stay in the SVG). Scope the rules — `class="subline"` on the root, `svg.subline { … }` and `svg.subline text { … }` rather than bare `svg` and `text` — so the document-scoped block no longer reaches other inline SVGs on the page (there are none today; the explorer in `interactive-explorer-for-stream-decodes` would be one). And let one figure theme apart from another by setting custom properties on its root element (`style="--bg-color: …"`), which is scoped to that element, where `css=` is not; verified alongside the token check. The `@import` of Source Code Pro goes: with `--font-mono` on the page the sublines draw in Fira Mono (also 0.6 em advance, so `char_width` holds), and the import would fetch a face the page never draws; the fallback for a standalone SVG is the machine's monospace.

Considered and set aside: a few lines of JS that fetch each sidecar and inline it at read time. It would give the same CSS participation with a lighter `index.html` (8–15 KB a figure, on an 80 KB page), but the page would then need JS and a fetch to show a figure at all: opened from disk, Chromium refuses `fetch` between `file://` URLs, so the offline bundle would lose its sublines, and the PDF print would have to wait on the fetches. The Markdown reader, who is the one that wanted the path data out of the way, already has the link.

**2026-09-22, done** — Landed as sketched, with the palette question settled the token way. CSS is now in these places, each with one job, and `lit.css`'s header maps them: `src/mini/lit/base.css` (tokens — now including `--font-sans`/`--font-serif`/`--font-mono` — type, code, the booktabs table, images, quotes, heading anchors), `src/mini/lit/lit.css` (the frame, figures, admonitions, swatches, the print rules the frame needs alone), `docs/report.css` (report polish and the whole print block, now also `table` kept whole and `h1`–`h3` kept with what follows, which used to be lit's), `scripts/md.css` (site-only rules; the build writes `base + md` to `_site/md.css`, and VS Code's preview lists both files), `src/mini/chips.css` and `src/mini/lightbox.css` (read by the constants that used to hold them), and `src/subline/theme.css` (scoped to `svg.subline`, reading `--bg`, `--fg-muted`, `--border` and `--font-mono` with its own values as fallbacks; per-figure overrides go through `Subline(vars=…)` on the root element).

`mini.reports.report_styles` finds `docs/report.css` beside the report tree, and `mini.lit.render.compose` inlines it last, so `./go render`, `./go serve` and the export all carry it; the exporter's own copy of that step is gone, and the two stale sentences in `docs/README.md` are corrected.

Checked against the pages before the change, in both themes and in print. The site index and ex-2.2.9 are pixel-identical on screen; `d2.2/design.md`'s table cells are the 0.1 em narrower that taking lit's padding over md's implies; ex-2.1.1's sublines now sit on the page's own dark (they were on `#181c1a` before, a slightly different dark than the page's `#1f1f1f`) and draw in Fira Mono. The two PDFs are identical page for page except the subline page, after one correction: the print body size was 11pt through `lit.css`'s print block, and `report.css` had it on `html` only, so moving the block dropped the body to 0.9 rem of that — `html, body` now. The `.sw-themed` / `.mini-themed-figure` theme-detection selector is still written out twice; harmless, and not worth a shared class for two rules.

Two report sources lost their `sub_css` override, so ex-2.1.1 and ex-2.1.2 want republishing; the stylesheet split reaches every other report on its next export (`staleness-check-misses-src-edits`).
